# Tilda Webhook → SMTP.BZ

Небольшой сервис принимает заявки Tilda, проверяет API key в HTTP-заголовке и отправляет письмо через SMTP.BZ. До доставки поля заявки временно хранятся в SQLite только как AES-256-GCM ciphertext. После принятия письма SMTP-сервером ciphertext сразу удаляется; максимальный срок недоставленной заявки — 7 дней.

Полная инструкция по безопасной подготовке VPS и запуску на Ubuntu Server 26.04 LTS находится в [DEPLOY_UBUNTU_26_04.md](DEPLOY_UBUNTU_26_04.md). Модель угроз, остаточные риски и краткий production checklist описаны в [SECURITY.md](SECURITY.md).

## Что реализовано

- `POST /webhook/tilda` для `application/x-www-form-urlencoded` и `multipart/form-data`;
- API key в настраиваемом заголовке, быстрый ответ для лимита Tilda в 5 секунд;
- корректная обработка установочного запроса `test=test` без отправки письма;
- durable SQLite outbox: AES-256-GCM, lease-восстановление, экспоненциальные повторы и HMAC-дедупликация;
- `/admin` с HTTP Basic: получатели, отправитель, тема, HTML-шаблон и статистика;
- `/admin/routes`: список форм, отдельная страница настроек каждого маршрута, собственное имя отправителя;
- `/admin/logs`: журнал SMTP.bz через API без сохранения в приложении;
- отдельное письмо каждому получателю, с повтором только неподтверждённых отправок;
- справочник фактически полученных переменных по формам без сохранения значений полей;
- HTML-экранирование всех значений формы и защита темы от подстановки заголовков;
- HTTPS через Caddy, healthcheck и контейнер без root-доступа.
- обычные access-логи отключены; отдельный журнал только для админки ротируется по размеру для Fail2ban (до 7 архивов).
- Fail2ban блокирует IP после 5 неудачных входов в админку за 10 минут.
- индексация всех URL запрещена через `robots.txt`, `X-Robots-Tag` и meta robots.

## Быстрый запуск

Требуется сервер с публичным IP, доменом и установленными Docker + Docker Compose.

1. Направьте A/AAAA-запись домена на сервер.
2. Создайте `.env` из примера:

   ```bash
   cp .env.example .env
   ```

3. Создайте отдельный keyring очереди. Команда использует криптографический генератор, создаёт два независимых 256-битных ключа и отказывается перезаписывать существующий файл:

   ```bash
   uv run python scripts/generate_queue_keyring.py
   ```

   Сохраните резервную копию `secrets/queue-keyring.json` отдельно от базы. Без неё ожидающие заявки восстановить невозможно. Не добавляйте файл в Git.

4. Заполните `DOMAIN`, три **разных случайных секрета длиной от 32 символов** и SMTP-параметры. Точный SMTP-хост, порт, логин и пароль возьмите в разделе подключения SMTP.BZ. Домен адреса отправителя нужно заранее верифицировать в SMTP.BZ. Ограничьте доступ: `chmod 600 .env secrets/queue-keyring.json`.
5. Запустите:

   ```bash
   docker compose up -d --build
   ```

6. Откройте `https://ваш-домен/admin`, войдите с `ADMIN_USERNAME` / `ADMIN_PASSWORD`, укажите получателей и отправителя.
7. В Tilda откройте **Настройки сайта → Формы → Webhook** и задайте:

   - URL: `https://ваш-домен/webhook/tilda`;
   - API key: имя `X-Webhook-Key` (либо значение `WEBHOOK_API_KEY_HEADER`);
   - значение ключа: значение `WEBHOOK_API_KEY`;
   - способ передачи: **в заголовках**.

   После сохранения Tilda отправит `test=test`; сервис ответит `200 ok`. Затем включите этот приёмщик в нужных формах и перепубликуйте страницы.

## Шаблоны

В теме и HTML можно использовать **любое** входящее поле по его точному имени, в том числе Unicode и пробелы: `{{ Name }}`, `{{ Phone }}`, `{{ Имя клиента }}`, `{{ utm source }}`, `{{ formid }}`. Специальные переменные:

- `{{ fields_table }}` — безопасная HTML-таблица всех полей;
- `{{ received_at }}` — время получения в UTC (только в HTML).

Неизвестные переменные становятся пустой строкой. Значения всегда HTML-экранируются.

`fields_table` и `received_at` зарезервированы. Если форма действительно присылает поле с таким именем, обратитесь к нему через явный префикс, например `{{ field:received_at }}`.

## Маршрутизация по формам

На странице `/admin/routes` показан список маршрутов и справочник полученных полей. Ссылка «Добавить маршрут» открывает `/admin/routes/new`, нажатие на название — `/admin/routes/{id}`. Каждый маршрут содержит:

- поле для сравнения, например `formid`, `formname` или собственное `form_route`;
- ожидаемое точное значение;
- отдельных получателей;
- имя отправителя (пустое значение наследует имя из общих настроек `/admin`);
- собственную тему и HTML-шаблон.

Например, маршрут `formid = form123` отправляет письмо Пете, а `formid = form456` — Маше. Если ни один включённый маршрут не совпал, используется письмо по умолчанию. При нескольких совпадениях применяется первый созданный маршрут.

По [официальной документации webhook Tilda](https://help-ru.tilda.cc/forms/webhook) системно гарантированы `tranid` и `formid`, где `formid` — ID блока формы. В [общей документации формы](https://help-ru.tilda.cc/forms/settings) сказано, что «Название формы» передаётся в сервисы приёма данных, однако `formname` не указан в спецификации payload webhook. Поэтому:

1. сначала отправьте настоящую тестовую заявку;
2. посмотрите в админке «Справочник полей форм»;
3. используйте `formname`, только если он действительно присутствует;
4. для гарантированной маршрутизации используйте `formid` либо добавьте в Tilda скрытое поле `form_route` с постоянным значением.

Справочник группирует фактически увиденные имена переменных по `formid`/`formname` и показывает время первого/последнего получения и счётчик. Значения полей не записываются. Лимит справочника — 5000 сочетаний «форма + поле», чтобы ошибочная или вредоносная схема не могла бесконечно увеличивать базу.

## Отдельные отправки и журнал SMTP.bz

Получателей можно разделять запятой, точкой с запятой или переносом строки. Повторяющиеся адреса без учёта регистра удаляются. Для каждого адреса создаётся отдельный SMTP envelope и заголовок `To`; другие получатели в письме отсутствуют.

При первой попытке настройки письма и список получателей фиксируются внутри зашифрованной очереди. После каждого принятого письма оставшиеся адреса сохраняются там же. При отказе одного адреса остальные всё равно обрабатываются, а после перезапуска повторяются только оставшиеся. Изменение или удаление маршрута не меняет уже начатую отправку. Старые записи очереди поддерживаются: получатели фиксируются при первой попытке после обновления.

Для журнала добавьте в `.env` отдельный `SMTP_BZ_API_KEY` из SMTP.bz → «Мой профиль», затем выполните `docker compose up -d app`. Ключ передаётся сервером в `Authorization` по [официальной документации](https://docs.smtp.bz/#/api); SMTP-пароль для этого не используется. Страница `/admin/logs` показывает до 50 записей с пагинацией, фильтрами по email получателя, датам и статусу. Это журнал всего SMTP.bz аккаунта, включая отправки других приложений. Если ключ не задан или API недоступен, страница объясняет причину; отправка писем продолжает работать. Ответ API не записывается в БД или файлы, HTTP-кэширование отключено.

## Эксплуатация и приватность

Сервис не хранит журнал заявок и не пишет содержимое ошибок SMTP. `/admin/logs` показывает журнал аккаунта, полученный напрямую от SMTP.bz. До доставки заявка существует в outbox только в зашифрованном виде. Исходный ключ подключается как Docker Secret к одноразовому сервису `prepare-keyring`. Он создаёт закрытую копию в томе `runtime-keyring`: каталог `0500`, файл `0400`, владелец — пользователь `app` из образа. Приложение монтирует этот том только для чтения. Исходный файл остаётся с правами `0600`; его владелец может быть `root`. Ключ отсутствует в SQLite, образе и Docker environment. После подтверждения всех получателей ciphertext удаляется. Отдельно постоянно хранятся только настройки, названия переменных, `formid`/`formname`, временные отметки и счётчики справочника — без значений полей. SMTP.BZ при этом получает содержимое письма и может вести собственный журнал доставки — это нужно учитывать в документах об обработке персональных данных.

Все ответы содержат `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet, noimageindex`, а `/robots.txt` возвращает `Disallow: /`. Это запрещает корректно работающим поисковым роботам индексировать сервис, но не скрывает сам домен и не заменяет авторизацию.

Webhook возвращает `200` только после SQLite `COMMIT` с `journal_mode=WAL` и `synchronous=FULL`. После аварии незавершённый lease истекает и заявка снова становится доступной worker. Повторы Tilda с тем же `tranid` подавляются HMAC-идентификатором, который хранится 7 дней и не раскрывает исходный номер заявки.

SMTP не поддерживает общую транзакцию с SQLite. Если процесс упал после принятия письма SMTP-сервером, но до сохранения подтверждения конкретного получателя, возможна повторная отправка. Сервис выбирает семантику **at least once**: редкий дубль предпочтительнее потери. Для уменьшения дублей каждое письмо получает детерминированный `Message-ID`, отдельный для каждого получателя, но окончательное решение о дедупликации принимает почтовый сервер.

При недоступности SMTP интервал повторов растёт от 5 секунд до 1 часа. Через 7 дней недоставленный ciphertext удаляется и увеличивается счётчик `expired`. Админка показывает только размеры `pending`/`retrying`, не содержимое очереди.

### Обновление после исправлений VPS

Сохраните действующие `.env`, БД и `secrets/queue-keyring.json`; повторно генерировать ключ нельзя. После обновления файлов:

```bash
docker compose config --quiet
docker compose pull caddy fail2ban
docker compose up -d --build
docker compose ps -a
```

`prepare-keyring` должен завершиться с кодом 0, затем `app` станет healthy. Исправлен тег Fail2ban на `crazymax/fail2ban:1.1.0`. Настройки существующих маршрутов обновляются автоматически при старте без удаления данных. Полная проверка Caddy на сервере: `docker compose run --rm --no-deps caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`.

### Ротация ключа очереди

Добавьте новую 32-байтовую base64-строку в `keys` файла keyring и измените `active` на её числовую версию. Старые ключи нельзя удалять, пока в outbox существуют записи их версии. Приложение проверяет это при старте и откажется запускать worker вместо уничтожения недоступных заявок. После опустошения очереди старую версию можно удалить, сохранив защищённую резервную копию keyring. После изменения исходного файла обновите закрытую копию и перезапустите приложение:

```bash
docker compose stop app
docker compose run --rm --no-deps prepare-keyring
docker compose up -d app
```

Обычный `docker compose restart app` не обновляет копию ключа. Том `runtime-keyring` содержит секрет: не включайте его в незашифрованные резервные копии вместе с БД.

Счётчик `failed` показывает попытки обработки заявки с ошибкой отправки, `expired` — заявки, не доставленные за TTL. Счётчик `sent` по-прежнему означает число заявок, отправленных всем получателям, а не число отдельных писем. Отдельные письма смотрите в журнале SMTP.bz.

## Локальная разработка

```bash
uv sync
uv run pytest
uv run uvicorn app.main:app --reload
```

Для локального запуска задайте переменные из `.env.example` в окружении. Файл `.env` приложение само не читает; Docker Compose передаёт его автоматически.

## Проверка webhook вручную

```bash
curl -X POST 'https://ваш-домен/webhook/tilda' \
  -H 'X-Webhook-Key: ваш-ключ' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'Name=Иван' \
  --data-urlencode 'Phone=+79990000000'
```

Ожидаемый ответ: `ok` с HTTP 200.

## Fail2ban

Fail2ban включён в `compose.yaml` и рассчитан на production-сервер Linux с Docker Engine и iptables/nftables. Контейнер получает только необходимые для firewall возможности `NET_ADMIN` и `NET_RAW`; полный `privileged`-режим не используется.

Защищены `/admin` и все вложенные страницы `/admin/*`, включая настройки форм и журнал отправок. После 5 ответов HTTP 401 с одного IP за 10 минут адрес блокируется на 1 час в цепочке `DOCKER-USER`. При повторных блокировках срок удваивается максимум до недели. HTTP/3 намеренно не публикуется, чтобы блокировка TCP-портов 80/443 не обходилась через UDP/443.

Проверка состояния:

```bash
docker compose exec fail2ban fail2ban-client status tilda-admin
docker compose exec fail2ban fail2ban-client get tilda-admin banned
```

Разблокировка своего IP:

```bash
docker compose exec fail2ban fail2ban-client set tilda-admin unbanip 203.0.113.10
```

Caddy пишет только обращения к админке в отдельный JSON-журнал. `Authorization`, cookie, API key, User-Agent и Referer удаляются; запросы webhook вообще не логируются. Caddy 2.10 ротирует журнал по размеру 10 MiB; хранится до 7 архивов, архивы старше 7 дней удаляются при ротации. Параметр `roll_at` не используется, поскольку он требует Caddy 2.11. Email из параметра фильтра `recipient` удаляется из access-лога. В журнале и базе Fail2ban остаются IP-адреса — это необходимо для блокировки и должно быть отражено в политике хранения технических данных.

Если перед Caddy находится Cloudflare или другой внешний reverse proxy, текущую конфигурацию Fail2ban применять нельзя: она увидит IP прокси. Сначала необходимо настроить доверенные диапазоны конкретного провайдера и его механизм блокировки.
