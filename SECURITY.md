# Security notes

## Реализованные меры

- Webhook принимает только form-urlencoded/multipart, ограничен 1 MiB и 200 полями.
- API key и данные HTTP Basic сравниваются в constant time.
- Три секрета должны быть разными, случайными и не короче 32 символов.
- Админка защищена HTTP Basic поверх обязательного HTTPS, CSRF-токеном, CSP и запретом кэширования.
- Значения заявки HTML-экранируются; переводы строк удаляются из темы письма.
- Приложение и Caddy работают с урезанными Linux capabilities и `no-new-privileges`.
- Приложение не доверяет proxy-заголовкам и не пишет access-логи.
- Caddy логирует только `/admin` и `/admin/*`, удаляя чувствительные заголовки и email фильтра журнала (`recipient`).
- Все маршруты закрыты от индексации через `X-Robots-Tag`, `robots.txt` и meta robots.
- Fail2ban блокирует перебор пароля в Docker-цепочке `DOCKER-USER`.
- SQLite использует WAL + `synchronous=FULL`; webhook отвечает только после durable commit.
- Поля ожидающих заявок защищены AES-256-GCM, исходный ключ подключается отдельным Docker Secret к `prepare-keyring`; приложение читает закрытую копию в томе `runtime-keyring` с правами `0400`, принадлежащую `app`. Сервис подготовки работает от root без сети и завершается до старта приложения.
- Справочник форм хранит только имена переменных, `formid`/`formname`, время и счётчики; значения полей туда не записываются.
- После SMTP `250 Accepted` ciphertext удаляется; HMAC-дедупликация не хранит `tranid` открыто.
- SQLite-файл и исходный keyring получают режим `0600`. Том `runtime-keyring` содержит копию секрета и требует той же защиты при резервировании.
- Зависимости устанавливаются строго из `uv.lock`.

## Остаточные риски

- Между SMTP `250 Accepted` и сохранением подтверждения получателя в SQLite остаётся окно редкой повторной отправки. Это at-least-once, не exactly-once.
- Недоставленная заявка хранится зашифрованно до 7 дней. Шифрование снижает риск утечки, но не отменяет сам факт временного хранения.
- Потеря keyring делает ожидающие заявки невосстановимыми; компрометация сервера с одновременно доступными БД и keyring позволяет их расшифровать.
- SMTP.BZ получает содержимое письма и может хранить собственные журналы доставки. Страница `/admin/logs` читает журнал через API, не сохраняя его локально; API-ключ находится только в окружении сервера. Настройки и оставшиеся получатели текущей отправки хранятся внутри ciphertext до завершения или TTL.
- Секреты из `.env` доступны root-пользователю сервера и администраторам Docker. На сервере файл должен иметь режим `0600`.
- Fail2ban требует `NET_ADMIN` и `NET_RAW`. Используется отдельный контейнер с закреплённой версией, но его нужно регулярно обновлять после проверки release notes.
- Конфигурация Fail2ban предполагает прямое подключение клиента к Caddy. При использовании CDN/reverse proxy необходима отдельная настройка доверенных IP и блокировки на стороне провайдера.
- Security-log и база Fail2ban содержат IP-адреса до 7 дней. Это технические данные, для них должна быть определена правовая основа и политика хранения.
- Названия формы и переменных сохраняются как техническая схема. Не помещайте персональные данные в «Название формы» или «Имя переменной» в Tilda.

## Production checklist

1. Сгенерировать три независимых секрета криптографическим генератором.
2. Создать keyring, сохранить отдельную защищённую резервную копию и выполнить `chmod 600 .env secrets/queue-keyring.json`.
3. Разрешить снаружи только TCP 80/443; не публиковать порт приложения 8000.
4. Проверить `docker compose exec fail2ban fail2ban-client status tilda-admin`.
5. Провести 5 тестовых неудачных входов с отдельного IP и проверить фактическую блокировку.
6. Настроить регулярное обновление ОС, Docker, Caddy, Fail2ban и Python lock-файла.
7. Ограничить SSH вход по ключам и отдельно защитить SSH системным Fail2ban или firewall.
8. Отправить тесты каждой формы, сверить справочник переменных и настроить маршруты по `formid` либо постоянному скрытому полю.
